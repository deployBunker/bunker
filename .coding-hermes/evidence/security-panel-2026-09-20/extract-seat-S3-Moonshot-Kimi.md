# 1. SIGN-OFF VERDICT

**DO-NOT-APPROVE** (for team use, today). The artifact is genuinely well-built in the parts it has thought about — rootless per-agent dockerd, per-user SSH key material, correct JWT algorithm pinning, a hash-chained audit log, a fail-closed `/tmp` boundary, and, unusually, honest runtime self-reporting when isolation is *not* provisioned. That is real engineering. But a security engineer approving this for a team is asked to sign off on four things that do not exist: **(a) a transport posture** — TLS is off by default, `Validate()` does not require it, the daemon serves plaintext on `0.0.0.0` with no warning, and the project's own recommended demo path (`README.md:166`) hands a **master token over cleartext HTTP to a public IP**; **(b) an operator identity model** — there is exactly one credential for the whole control plane, shared by every engineer, and the audit trail labels every one of them `caller: "master"`, so `destroy` of a colleague's agent is unattributable; **(c) enforced mTLS identity** — `SECURITY.md:24` advertises "mTLS between CLI and server", the `MTLSAuth` interceptor that implements client-cert *identity* is never constructed anywhere in the tree, and `tls.verify_cn` is read by no code; **(d) authorization symmetry** — `Agent/Heartbeat`, the only "renew" verb, has **no ownership check at all**, so any agent's scoped key renews any other agent's TTL, while `GetAgent`/`Metrics`/`Exec` do check.

Biggest single reason: **the security model is documented in one place and enforced in another.** `SECURITY.md`'s five bullets describe a stricter system than the code implements (mTLS identity, JWT-scoped auth as the default, tamper-evidence), and the code enforces controls the docs never name (the `/srv/bunker-share` group-readable exchange, the mutable `get.docker.com` installer, the disposable in-memory key store). A security team's first move on a vendor artifact is to diff the claims against the behaviour; here that diff fails on three of five bullets, which makes everything else in the doc untrustworthy — including the parts that are true.

## B — Agent isolation

**C-6 | CONTRADICTED as written — must be re-worded.** `SECURITY.md:30`:

> *"Out of scope: social engineering, physical access, compromise of the host system by a user with root in their own container (containers are designed for root access)."*

For an individual operator this is defensible scoping. For a **security-team** audience it inverts the trust model: the container is the workload; the **host is the platform** the team is being asked to trust. As written it announces "root in a container may own our host and we've decided not to care", in a product whose entire sales claim is *"complete isolation"* (`README.md:43`). It is product risk, not kernel reality, and it will lose the review on the first read.

Recommended replacement wording (ship this instead):
1. **Name the real boundary:** "Bunker's isolation boundary is the **Linux user account**, not the container. An agent with root inside its own container holds exactly the privileges of its host account, plus the kernel's container attack surface. Container-escape to the host is out of scope; **cross-agent isolation is in scope and enforced.**"
2. **Split the scope into three labelled lists** — IN SCOPE (agent→other agent files/data/TTL; agent→control plane; agent→host files it should not read; image and installer supply chain; egress; audit-trail integrity), OUT OF SCOPE (host root; kernel/container-runtime 0-days; physical; social engineering), ASSUMED (an up-to-date host kernel and rootless-Docker stack; per-agent-host tenancy; operator SSH keys are trusted).
3. **State the residual the container *does* add:** a container escape in a rootless, userns-remapped setup escalates to the *agent's own* host user, not to root — say so, because it is the strongest honest sentence the document can carry, and it is currently missing.
4. **State the shared-scratch read model explicitly** (see C-8), because "out of scope" plus an undocumented group-readable exchange directory is exactly the combination that reads as concealment.

**C-7 | VERIFIED for the two claims it names; SPLIT on the third.**
- *own dockerd per agent* — **VERIFIED.** Per-agent transient unit `bunker-docker-<id>` with per-agent socket: `isolation.go:109-144` (unit argv, `--host=unix://<sock>`, `--setenv` PATH/HOME/`XDG_RUNTIME_DIR`/`DOCKERD_ROOTLESS_ROOTLESSKIT_NET=slirp4netns`), socket dir created and chowned to the agent at `manager_spawn.go:356-365`.
- *userns remap* — **VERIFIED.** `configureSubIDs` writes `/etc/subuid`+`/etc/subgid` (`rootless.go:535-557`); non-root dockerd path is the rootless installer + `rootlesskit` (`rootless.go:190,224,450`).
- *SSH key isolation* — **SPLIT.** Material: verified (`manager_spawn.go:337-341`, `0600`, dir `0700`, root-owned; only the pubkey reaches the agent at line 305-311). Capability: **not isolated** — no `restrict,command=` (see C-1). Nothing in this repo is merely aspirational in the *mechanical* sense: every claim above has code behind it. The failure is the *wording* of the third, not the machinery.
- **A strength worth recording:** isolation state is *reported, not assumed*. `ServerInfo.TmpIsolation` returns `private` / `host-shared` / `unknown` from a live host probe (`service.go:154-245`, cache-once at 243-248), a daemon that is not root says so (`service.go:177-179`), and `README.md:660-680` warns that the feature is build- and provision-dependent. This is the right pattern and it is the reason my verdict says "well-built in the parts it has thought about".

**C-8 — the answer. What host-accessible surfaces does an agent still have beyond its own container?** Six, in descending security-team interest.

1. **Every other agent's shared-scratch directory — read access is by design.** `hostsetup/scratch.go:12-13` documents the tree as `/srv/bunker-share/<agent-id>` = `bunker-<id>:bunker-agents` mode `2770`, and `scratch.go:36-46` fixes `ScratchDirMode=0o2770` with a tmpfs mounted `size=…,mode=0770,nosuid,nodev`. Group `bunker-agents` is every agent (`isolation.go:201-205` grants membership to **every** spawn, independent of the scratch toggle). Therefore **agent A can read any file agent B stages in `/srv/bunker-share/B/`.** The docs call it "the only sanctioned cross-agent exchange point" — a euphemism for "a shared, group-readable directory". No per-pair ACL, no opt-in by the reader, default ON (`config.go:437` `SharedScratchEnabled: true`).
2. **A full SSH session under its own key, with forwarding enabled** (C-1/C-7): `-L`/`-R`/`-D` (a SOCKS proxy *through the host's network position*), agent-forwarding, X11, and SFTP — because `manager_spawn.go:305` never writes `restrict`.
3. **Unrestricted outbound internet as the agent user.** Rootless dockerd runs `slirp4netns` (`isolation.go:95`); there is **no egress control in the tree** — `grep -rniE "egress|iptables|nftables|firewall" --include=*.go internal/ | grep -v _test` returns only the `SKIP_IPTABLES=1` rootless-installer constant (`rootless.go:134`), i.e. the daemon deliberately *skips* managing iptables. Confirmed by the board: `GAP-076` "Per-agent network egress policy… agents currently reach the internet freely" — **pending** (line 135).
4. **Host-bound ports in its allocated range.** Rootlesskit's `PortManager` binds on the host (`DOCKERD_ROOTLESS_ROOTLESSKIT_PORT_DRIVER=builtin`, `isolation.go:96`); per the project's own skill these serve on the tailnet, which is a host-reachable surface beyond the container.
5. **Anything world-readable on the host filesystem**, most importantly `/etc/bunkerd/config.yaml` — which holds the **master token** and the **JWT secret** (`config.go:96-99`). No code enforces a mode on the config file; if an operator's config is `0644` (the natural result of `tee` or a copied example, and `config.example.yaml` is `-rw-rw-r--`), every agent on the box can read the credential that owns the box. There is no startup check, no warning, and `SECURITY.md` never mentions it.
6. **The unauthenticated control-plane routes** (`server.go:114-169`) — `/healthz` plus the hilo graph endpoints, reachable by any agent on the host.

What A can **not** do: read B's home (`/home/bunker-B`, owner-only), read or write B's Docker socket (`/run/bunker/B`, `0700`), read B's `/tmp` (pam+`PrivateTmp`), read the bunkerd audit log (`0600` root), or use B's SSH key (never leaves the daemon). Those boundaries are real and verified.

## C — Provisioning & supply chain

**C-9 | VERIFIED (no injection) / SPLIT (a quoting defect and a TOCTOU class).**
- **No injection found in the spawn pipeline.** `agent_id` is validated `^[a-z0-9-]{1,63}$` (`agent/manager.go:25`) before every use (`manager_spawn.go:43`; re-checked at `manager_destroy.go:194`, `manager_lifecycle.go:140,236,283`, `registry.go:272`, `ssh_key_cleanup.go:40`, `manager_destroy_containers.go:29`). Every host command is argv-only: `useradd -m -s /bin/bash <username>` (`manager_spawn.go:222`), `chown … username <path>` (294, 314, 332, 363, 375, 470, 616), `systemd-run` with `--property=` argv (`496`, `isolation.go:109-144`), `pgrep`/`kill`/`systemctl`/`journalctl` (`773-923`). No interpolation into a shell string anywhere in the spawn path. Clean.
- **Defect: the `--script` upload path corrupts script bodies twice over.** `buildAgentScriptCommand` (`service.go:1179`) applies POSIX single-quote escaping to the script body — `escaped := strings.ReplaceAll(scriptContent, "'", "'\\''")` — but the body is then placed inside a **quoted heredoc** (`<<'EOFSCRIPT'`, line 1181), where the shell performs **no** interpretation; the escape is doubly wrong there and lands as literal `'\''`. I re-ran the exact pipeline end-to-end through `bash -c` (`/tmp/panel_exec_script_probe.py`): a body containing one apostrophe lands on disk as `echo "quote '\'' inside"`, and `sh` then mis-parses it (the probe's run printed `quote '\'' inside`). Any generated script containing a single quote (`echo 'x'`, `trap '…' EXIT`, `awk '{print}'`) is silently mangled; the *command* path is unaffected because it uses `shellQuoteSingle` correctly. Existing quote-related tests all use apostrophe-free bodies (`internal/server/exec_image_test.go:84-85`, `disclosure_test.go:357`).
- **TOCTOU / state-reuse class (already known, still live).** UID recycling between destroys and spawns: `spawn_uid_recycling_test.go`, `spawn_recycled_uid_residue_test.go` exist precisely for it, `INT-CI-026` (pending) reports the residual flake, and `DF-BUNKER-24-LIVE` (pending) says the orphan-key cleanup is committed but *"NO host runs it"*. The class is "a destroyed agent's uid/keys/socket-path residue is re-used by the next agent" — a cross-tenant confusion surface with a live gate still owed.
- The daemon writes the temporary private key into `os.TempDir()` on the daemon host (`manager_spawn.go:257`), root-owned `/tmp` (the agent's private `/tmp` is the agent's, not root's). `ssh-keygen` defaults to `0600`; no mode is asserted by the code and no test pins the cleanup.

**C-10 | SPLIT — one path is pinned and verified, the other is the worst in the artifact.**
- **Binaries: VERIFIED-good.** `scripts/install.sh:7-20` documents "verify first, then install"; `require_sha256_tool` (265-269) refuses if no sha256 tool exists; `verify_file` (289-309) refuses with exit `42` on a missing entry, a malformed entry, or a digest mismatch, and the release must carry `SHA256SUMS` plus `install.sh` among six named assets (`internal/releasecheck/releasecheck.go:87-94`).
- **Installer delivery: SPLIT.** The documented primary path is `curl -fsSL https://github.com/deployBunker/bunker/releases/latest/download/install.sh | sh` (`install.sh:5,87`) — the **installer itself is unpinned, unsigned and unverified**, and `SHA256SUMS` is fetched from the same origin over the same channel as the binaries. That is integrity against corruption, not against a compromised release or a swapped sums file. No GPG/sigstore, no `--tag` requirement, no digest pin in the README.
- **Rootless-docker installer: CONTRADICTED (no pinning, no verification, executed as the agent).** `rootless.go:22` — `const rootlessInstallURL = "https://get.docker.com/rootless"`. `downloadRootlessInstaller` (rootless.go:242) is `curl -fsSL -o <path> <url>` with **no checksum, no signature, no version**. The downloaded script is then executed **as the agent user** (`rootless.go:190,224,450` run `su - <user> -c <session command>`). GAP-091's cache (`config.go:410`, `/var/cache/bunker/rootless-installer`, root-owned `0755`) is a good availability fix that **also makes a poisoned installer persist across every subsequent spawn**. This is the highest-value supply-chain gap in the artifact: mutable upstream artifact → arbitrary code in agent context → host-side persistence via cache.
- **Adjacent, undocumented in the security model:** `scripts/install-exec-audit.sh:16-42` installs `snoopy` via `apt-get` (distro-signed, acceptable) and appends it to `/etc/ld.so.preload` **host-wide** (`:65-69`) — an `LD_PRELOAD` interception layer across every process on the box. It is not invoked by `hostsetup` (`grep -rn snoopy internal/` → empty) and it is not mentioned in `SECURITY.md`.
- **No SBOM, no provenance attestation, no cosign, no image policy.** `GAP-063`/`GAP-064` (container mode + per-agent image customization) are `complete`, `image_spec.enabled: true` by default (`config.go:402`) — so a spawn can build from an agent-supplied spec — and there is **no repository allowlist, no digest pinning, no signature policy, and no registry egress rule** anywhere in `internal/imagespec`. For a team, "which images may run on our hosts" has no answer.

## D — Audit & forensics

**C-11 | SPLIT — tamper-*evident* for a nonspecific attacker, not tamper-*proof*, and defeatable by the two attacks that matter.**
- **The chain is real.** `audit.go:334-352` computes `hash = SHA-256(canonical line with the hash field emptied)` and binds `prev_hash` to the previous record; rotation preserves the link (`audit.go:377-437`, `lastHash` survives); `verify.go:37-87` walks `.3→.2→.1→live` enforcing both per-record digest and cross-file chaining; restart re-seeds the head from disk (`audit.go:164-178`, DF-BUNKER-29). The convention is shared between writer and verifier, not reimplemented.
- **Attack 1 — tail truncation is invisible.** `Verify` reports clean for a file whose last N lines were removed: every remaining record chains, and nothing out-of-band attests to the expected head. There is no head-anchored witness by default.
- **Attack 2 — full rewrite is invisible.** The digest is unkeyed and unsalted, and the algorithm is public, so anyone with write access to `/var/log/bunkerd/audit.log` can edit any record and recompute the entire chain forward. If the file is deleted entirely, `reseedChainHead` starts a fresh genesis (`audit.go:164-177`, `prev_hash:""`) and `verify` passes on the new chain.
- **The only real cryptographic binding is opt-in.** `audit.seal_key` (`config.go:121`) appends an HMAC-SHA256 seal per rotation (`audit.go:427-435`, `writeSealRecordLocked:363-375`) — **empty by default**, and per `config.example.yaml` it must be kept secret *and* backed up with the shipped copies for the proof to mean anything. Remote shipping (`audit.ship_to`) is likewise **off by default**, and an invalid `ship_to` degrades to local
-only logging with a warning (`server.go:66-75`) — so the "loud failure" is a warn-and-continue, not a refuse.

**So, precisely: what can an attacker with root *inside the agent's container* do to the trail?** Nothing directly — the log is `0600` root-owned on the host (`audit.go:130`), and the agent is an unprivileged user. But that is the wrong threat model for this artifact, because the agent's root is *contained*, and the trail's real exposure is the **agent's host user**, which is not the same as container root and is *not* contained:

- The agent host user cannot write the log, but can it **delete** it? Only if it can write the *directory*. `audit.go:126` creates the parent `0700` root-owned, so no. Good — but only if the daemon created it; a pre-existing `/var/log/bunkerd` with loose modes is never re-asserted (there is no mode-stat-back for the audit dir, unlike `scratch.go:124-145` and `tmpnamespace.go` which do stat back).
- What the agent **can** do is deny service: fill `/var/log` on the host filesystem (outside the cgroup `LimitFSIZE` path only if it can write there — it can't) — so this is weak. Honest answer: **the agent-side host user cannot tamper with the audit chain.**
- The attacker who *can* is anyone who obtains the master token (C-2/C-3), or host root. Host root is explicitly out of scope (`SECURITY.md:30`). Master-token compromise is out of scope *implicitly but is the live risk* — and note what happens then: the trail keeps recording faithfully and attributing everything to `caller: "master"` (`interceptor.go:144-163`), so a forensic reader cannot distinguish the attacker's spawns from the team's. **The tamper-evidence is fine; the attribution is not.** That is the more damaging finding for an incident responder, and it is a design property, not a bug.

One more: `interceptor.go` records **only authenticated requests** by construction (`server.go:208-219` comment). Failed authentication never produces a record. So **brute-force and token-guessing attempts are invisible in the audit trail** — there is no auth-failure log at all. For a SOC reviewer that is a first-question failure: "show me your failed-auth log."

**C-12 | SPLIT — good for "what happened", poor for "who did it" and absent for "was it attacked".**
- **Present and genuinely useful:** `bunker audit verify` (chain, first bad record index, non-zero exit — `verify.go:37`), `bunker audit list` (filters: agent, method substring, since/until, limit — `audit.md:143-151`), `bunker audit export` (lossless JSONL, hashes preserved — `audit.md:196-198`), `bunker audit status` (chain head, file/backup sizes, rotation lower bound, ship state, seal state — `status.go:13-46`, `audit.md:55-114`), and a **remote** `QueryAudit` RPC so an operator need not ssh in (`service.go:921-969`, `docs/audit.md:16-20`).
- **Missing for incident response, in order of severity:**
  1. **Attribution.** `caller` is `master` for every master/static-token caller and every unscoped JWT (`interceptor.go:157-162`). With one token per fleet, all team actions are one identity. There is no per-operator key, no session id, no client-cert subject (the mTLS path is dead — C-2), and no `GAP-095` delivery: the board row for **session attribution on the exec path** is **pending** (line 242).
  2. **Not an execution log.** `summarize()` deliberately omits request contents — no command, no args, no script body (`interceptor.go:206-219`). For `ExecAgent` the audit record says only *"ExecAgent agent_id=X"*. `docs/exec-audit.md` is explicit that exec-level capture is a **separate, unprovisioned** layer: snoopy via `scripts/install-exec-audit.sh`, not called by `hostsetup`, `grep -rn snoopy internal/` → empty. So on a host built per the README, **"what did agent X run?" has no answer.** (GAP-048 is marked `complete`; the script exists; nothing runs it.)
  3. **No auth-failure records** (above) — no brute-force signal.
  4. **No integrity affordance in the query surface.** `QueryAudit` returns records but the responder must remember to run `verify`, and `audit.md:103` states plainly that **"last verify" is always `n/a`: verify history is intentionally not tracked anywhere.** So nothing continuously attests the chain is intact; a responder cannot tell whether the log was clean an hour ago.
  5. **No retention/immutability policy.** 5 MiB × 3 backups (`audit.go:20-26`), then gone; no WORM, no off-host anchor by default, no legal-hold, no time-bounded retention statement.
  6. **`audit status` can be wrong about the head on a tampered file** — `inspectLive` deliberately skips chain enforcement and reports the last *parseable* record's declared hash (`status.go:124-150`, documented at `audit.md:92-95`). It is honest about this, but a triager reading status alone can read a forged head as truth.

## F — Operational security

**C-14 | The single most likely real-world incident.**
- **Scenario:** A team adopts Bunker for its engineers; each engineer gets the one master token in their CLI config or `BUNKER_TOKEN`. The daemon runs with the default `tls.enabled: false` (C-3) on `:8080/:9090`. Engineer A on a café network runs `bunker connect`/`exec` in cleartext HTTP; a passive attacker on the path captures the bearer token. They now call `DestroyAgent` against every agent on the host, or `SpawnAgent` until `max_agents` (`config.go:393`, default 100) saturates, or `ExecAgent` into any agent (which is `docker run` / `sh` as the agent). The audit trail records it all as `caller: "master"` (`interceptor.go:157-162`), so nobody can tell it was not Engineer A. There is no failed-auth record, no alert, and the trail's only tamper defence (an unkeyed chain, `audit.go:334-352`) does not stop a legitimate-looking destroy.
- **The missing control is not one thing but the *first* one:** **there is no way to answer "who is this request from?"** — no per-operator credential, no enforced TLS, no enforced client identity, no attribution in the log. Everything downstream (RBAC, per-operator blast radius, incident response) is unreachable until that exists.
- **Second-most-likely:** an agent reads `/etc/bunkerd/config.yaml` and gets the master token (E), because the mode is unenforced and the docs never tell the operator to lock it down. That converts the *contained* agent into a *tenant escape* via the control plane — the sharpest edge in the artifact, because it needs no kernel bug at all.
- **Third:** a poisoned `get.docker.com/rootless` (C-10) executed as every new agent, cached root-owned at `/var/cache/bunker/rootless-installer`.
