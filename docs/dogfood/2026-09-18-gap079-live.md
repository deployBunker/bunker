## 0. The discriminating control — the same probe on the pre-fix CLI

A green probe run proves something only if the *same* probe is **red** on a build that
predates the fix. The control binary is `acfe850` — the revision immediately before
`1295b86`, built locally with `git archive acfe850 | tar -x` + `go build` (proto
generated code is committed in this repo, so no `buf generate` is needed) and stamped
`Commit=acfe850`; sha256 `37ed34965ae0798b03bd9156eaf60ea2582f2554caba0b1af1852aa9b523cb60`.
It was copied to the host as a *scratch* binary (`/root/gap079-live/bin/bunker-prefix`);
it was never installed over the host's CLI.

The probe (`tooling/tunnel_probe.py`, sha256
`fdf2fd838dacfe7884d4eb7dc13681f96bd0929b2e211bee2a800f0332d945f9`) starts
`<bin> tunnel gap079live` in a NEW session (so nothing but the CLI pid is ever
signalled), waits for the ssh child whose parent **is** the CLI pid, optionally proves
the tunnel carries `docker version`, then sends `SIGTERM` (reap path) or `SIGKILL`
(kernel `Pdeathsig` path) **to the CLI pid only** and re-reads `/proc`. Liveness is read
from `/proc`, so an exited-but-unreaped process is reported as state `Z`, never as
"alive".

process-table shape the checker looks for, and nothing more. It is counted (fail), and
after a by-PID kill the same checker passes again, so a `0` from this check is a real
measurement, not a matcher that cannot match.

## 11. What this does NOT claim, and the honest limitations

1. **The `0` forward count is a snapshot, not a temporal guarantee.** The row's criteria
   are process-table measurements at the moment of the check, and the battery's own check
   deliberately has **no age filter** (an orphan from an earlier run still counts). The
   measurement proves no forward — orphaned or live — existed at 21:56:04Z (and again
   after run 2); it is not a continuous monitor.
2. **Two harness artifacts are recorded rather than hidden.** (a) `03-phaseA-interspersed-artifact.log`:
   the *first* attempt at the control phase was started with a piped `bash -s`; when the
   local `ssh` was killed after a token-extraction bug, the remote shell kept running and
   both runs wrote into the same local log, so that file interleaves two attempts (one of
   which failed `connect` and never spawned). The clean re-run is
   `01-…-control-prefix-cli.log`; the artifact is kept because it contains the same
   leak signature measured independently. (b) The first *battery* transcript
   (`08-…`) ends at the battery's own `VERIFY-PASS` block and does **not** carry the
   wrapper's `BATTERY_EXIT_CODE`/`BATTERY_END_UTC` lines: the phase script was piped into
   `bash -s`, and the remote shell exited 0 with those two `echo`s unexecuted — its stdin
   reached EOF early. The only stdin consumer in the battery or the nested suite is the
   `ssh -i <agent-key> …` invocation in section 15 (no `-n`; there is no bare `read` in
   either script), so a child of the battery consumed the caller's stdin and the shell
   never read the rest of the script. That is a property of *the wrapper*, not of the
   battery verdict — hence run 2, which invokes the phase script **as a file** (nothing
   left on stdin to steal) and captures `BATTERY_EXIT_CODE=0` explicitly.
3. **The control binary is a locally built pre-fix revision**, not a binary taken from a
   host (`acfe850`, `git archive` + `go build`, sha256 in §0). It contains neither
   `1295b86` nor `cc61695`, which is exactly what makes the two probes discriminating.
4. **`bunker-las-02` is out of scope.** That host still runs an older build
   (`cef10fc`-era) and was not touched; nothing here certifies it.
5. **Scope of the probe.** It proves the tunnel CLI's ssh child is gone (state `GONE`,
   no `/proc` entry) after `SIGTERM` and `SIGKILL`, that the forward is released
   (port 2376 no longer bound), and that the tunnel still carries `docker version`
   before the signal. It does not exercise `bunker cp`/`deploy`/`mount`/`ssh` — the
   *same* orphan class outside the tunnel command is the subject of the already-filed
   `GAP-084` and was deliberately not fixed here.
6. **No board state was touched.** The row is still `pending`; no `.coding-hermes/board/*`
   file, no `.gitreins/*` file and no board row was modified by this worker. (The
   pre-existing `.gitreins/tasks.yaml` modification in the working tree is not ours and
   was not staged.)
