Bunker WebDAV — where we are

State of the WebDAV server + FUSE client and the Muster transports · 27 September 2026 · bunker@7edc54f · muster@feffb4e7 · both at parity 0 · 20/20 release rows closed
The one-line answer: the HTTP/WebDAV path wins decisively for reading — it removes the whole-tree stall class that made sshfs unusable — and it is not yet safe for editing a working tree. Four open P0 defects, three of which share a single root cause. That root cause is the next thing to fix, and it is also the thing that unlocks the largest remaining speed win.

1 · What is actually built

Server — bunkerd WebDAV surface

  • One handler across HTTP/1.1, HTTP/2 and HTTP/3; Alt-Svc advertised only while h3 is genuinely listening
  • HTTP/1.1 still works — proven with a real curl: GET/HEAD/OPTIONS 200, PROPFIND 207, PUT 201 with bytes confirmed on the server's disk, DELETE 204, stale If-Match → 412 with a parseable interoperable body, old User-Agent 200, no Accept header 200
  • Extensions: identity, if_match_refuse, rev, tree, op, watch
  • One-call snapshot op — fetch a whole tree in a single request
  • Conditional PUT (optimistic concurrency) — one request where staging-then-publish cost 1,023

Client — bunker-fs (Linux first)

  • Full read/write FUSE filesystem, 16 methods
  • Bounded cache — 256 MiB, LRU-by-hit
  • Concurrency knob — the lever that actually beat sshfs
  • One-call snapshot at mount — the lever for a whole tree
  • Own failure classifier and its own not-hang bounds
  • No symlinks, no xattrs, no readdirplus — and symlinks corrupt on write-back (BFS-018)

Muster

  • HTTP/2 and HTTP/3 client transports, both selectable
  • Protocol read from the response, never from the config — the release's trap: a response object alone would have passed and been wrong
  • Real .proto round-trip, asserted on content (names, field numbers, types, nesting), not on shape

2 · The measured numbers

Reading a whole tree — one call instead of a thousand

WhatNumberVersus

Snapshot walk, Helsinki DC (192 ms RTT)110 msno-snapshot 1,210 ms = 11.0×

The 110 ms is the interesting part. It is identical at both DCs even though the per-request floor differs by ~200 ms between them — because the tree is fetched once, at mount, so the walk is then served locally and does not move when the link gets slower. That is a property of the design, not of a simulated link: a delay relay predicted 12.0× and the real DC measured 11.0×.

Why it beats sshfs — two separate mechanisms

LeverEvidenceEffect
Concurrency8 parallel cold readsMAX 8 in flight, 3.6× wall — but a serial walk stays 1–2 in flight, 1.03×

These are independent, and conflating them is the mistake the release was built to avoid. Concurrency does not rescue a whole-tree operation — NFS is kernel-parallel and still stalls 33–36 s. The snapshot does. The client has both.

Against sshfs's stall class, this is the whole point: an operation ends in bounded time with an error, rather than blocking forever. Acceptance 8 (not-hang) was proven by killing the server live — the mount returned rc=1 in 0 s with "Transport endpoint is not connected" and stayed mounted rather than wedging.

3 · The both-datacentre rule — half discharged

Topology — DONE

Measured on two genuinely different DCs, live bunkerd hosts untouched:

  • Helsinki (dedi-2, direct, 192.9 ms RTT) — snapshot 110 ms / no-snapshot 1,210 ms = 11.0×
  • Falkenstein (bunker-mvp) — snapshot 110 ms / no-snapshot 1,612 ms = 14.7×
  • Falkenstein has ufw INPUT DROP, so it was carried over an SSH tunnel rather than opening a hole in a live host's firewall

Stalls — NOT discharged

The "0 stalls" claim still rests on a loopback battery. The DC legs measured walk times, not stalls.

And I did not paper over it: the committed battery cannot measure stalls at a DC — its write-verification cells read a local tree, so aimed at a remote server they would verify a stale mirror and go green while proving nothing. Filed as BFS-034, in flight.

This is why the rule is stated as topology measured, stalls loopback-only, gap named — rather than "0 stalls on both DCs", which I could have produced in one command and which would have been false.

5 · Declared but not built

ClaimReality
The client's invalidation / watch channel Advertised in the extension list; no working mechanism. The client reports this honestly in its own status record (channel_available: false) — the honesty is deliberate and I required it be preserved.
Bunker op catalogue (E-4) 2 of 8 implemented (capabilities, snapshot). status, diff, rev-parse, ls-files answer capability_unavailable, "slice C5".
Server-side delegation Not implemented. This is the ~80× whole-tree win from the PRD, and it is load-bearing, not an optimisation — the FUSE binding alone provably cannot short-circuit a whole tree (BFS-003: NFS is kernel-parallel and still stalls).
Windows Decided: WinFsp via cgofuse. The OS redirector was rejected because it cannot express the concurrency knob or carry the snapshot op — i.e. exactly the two things that made the client fast, decided against this release's own measurements. Not built. Mint: no work.

6 · The path to "safe for editing"

Ordered by what actually unblocks what — not by priority label:

#RowWhy it's here
1026 — the channelRoot of 024 and 033. Either implement the poll op or remove the claim and enforce a bounded, reported staleness window. Everything else is downstream of this decision.
2030 — > empties a filePure data loss, independent of 026. The only P0 that isn't about staleness.
3031/032 — the bound and the counterCheap, and they make the cache's own guarantees trustworthy. A bound the owner can't see is not a bound.
4018/019/020/021 — symlinks, readdir, rename, appendThe POSIX surface a real working tree needs. Until these land, "edit a git repo through the mount" is not a supported claim.
5E-4 slice C5 (delegation + the four ops)Not needed to be correct — needed to be fast on whole trees without the snapshot at mount.
The honest headline: the client is a genuinely good reader today and a risky editor. Reading immutable data is safe. Pointing it at a working tree you care about is not, and will not be until items 1–4 are done.

7 · The decisions I need from you

Decision 1 — the invalidation channel blocks 3 rows

File: docs/prd/PRD-bunker-fs.md §slice C5 + the events/watch op pair.

Two defensible answers, and I want your call because they buy different things:

  • (a) Build the server-side poll op — the real fix. The server's own 501 text already names the shape: "poll with HEAD/ETag or an X-Bunker-Op: snapshot diff". Cost: 1–2 days. Unlocks correct invalidation and starts the slice-C5 family.
  • (b) Remove the claim and enforce + report a bounded staleness window (TTL-only). Cost: 2–4 hours. Closes 024/033 as honest bounded behaviour rather than correct behaviour — the client stops lying about a channel it can't have, and you can see the window.

My recommendation: (b) now, (a) next. (b) removes a false claim cheaply and makes the failure mode visible and bounded; (a) is the actual unlock and is the same work slice C5 needs.

Decision 2 — the DC stall instrument

File: probes/bunker-fs-battery-wan.sh (the in-flight BFS-034 deliverable).

To close "0 stalls on both DCs" I need a battery whose write verification crosses the same link as the write — read back server-side over SSH, or compare authoritative hashes over the wire — plus a negative control proving the old approach misses a deliberately broken write. Cost: ~1 day for the instrument, ~1 hour per DC run.

Until then the rule stays honestly half-discharged rather than closed with a number I can't defend.

Standing item — the one thing I can't do without you

Host disk. ~/.hermes is 170 GB and root is at 92% (140 GB free). Growing the fleet will hit this before the fleet runs out of room. I've not deleted anything on your behalf.
