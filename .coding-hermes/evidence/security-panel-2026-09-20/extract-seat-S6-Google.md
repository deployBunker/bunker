# 1. SIGN-OFF VERDICT

**DO-NOT-APPROVE** for a team today. The control plane is a shared-secret, single-tier daemon whose *only* real credential is world-readable on a live host in this very fleet (`/etc/bunkerd/config.yaml` is `0644 root:root` in a `0755` dir), while that same daemon serves spawn/destroy/exec in **cleartext on every interface** (`ss` shows `*:10002`/`*:10001`, and the live config has no `tls:` section at all). Everything the project does well — the hash-chained audit log, the per-agent systemd unit, the fail-closed PAM/private-`/tmp` boundary — is downstream of a credential and a transport that are not protected. Second, the published security model advertises mTLS and container-root containment as properties, and the mTLS half **does not run in any connect-go deployment**: `TLSConnectionStateFromContext` reads `http.ServerContextKey`, which `net/http` defines as `&contextKey{"http-server"}` (i.e. a `*http.Server`), never an `*http.Request`, and nothing in connect-go v1.21 sets that key.

**Single biggest reason:** the control-plane secret is readable by the principal it is supposed to control, and the channel carrying it is unencrypted by default — so an agent does not need a kernel escape to own the box; it needs `cat`.

The engineering quality is genuinely above average (seams, table tests, honest comments, GAP rows for real gaps). That is *why* the auth/mTLS/transport findings are damning rather than forgivable: the same rigour was applied everywhere except the two things a security team reads first.

# 6. REPEAT-OFFENSE SECTION

**(a) Credential/key paths leaking.** The live host leaks the master token through a 0644 config (verified: `sudo stat -c '%a' /etc/bunkerd/config.yaml` → `644`), and the client-side leak class was already found once (DOGFOOD-014, board `tasks.jsonl:82` — 66 stale keys in `~/.bunker/keys/`). The server-side sibling of that row is unfixed: `manager_destroy.go:380-407` deliberately **keeps** a persisted private key it cannot attribute. Same class, server side, still open. Also `internal/cli/config.go:33,157-158` persists the token per server entry, and `internal/cli/spawn.go:~180` persists agent keys — the write path is careful (0600) but the *review* path never asked "who else can read the daemon's copy."

**(b) Success-marker string checks treated as state.** `internal/agent/manager_spawn.go:225-231` decides "the user already existed, so reuse it" by `strings.Contains(string(out), "already exists")` — a localized/updated `useradd` message silently flips a reuse into a **fatal spawn failure**, and the branch that *should* be a structured probe (`user.Lookup` + Home ownership) is prose matching. Same idiom in the destroy/force path (`manager_destroy.go:~400`, "userdel failed, treating agent as not found").

**(c) State ladders.** `agent.StopAgent/StartAgent/RestartAgent` treat presence in the tracker's status string as authority (`manager_lifecycle.go` + `service.go:390-418` route anything unknown to `CodeInternal`), while the durable registry (`registry.go`) is the real state — two sources, no reconciliation between "status string" and "registry event", and the lifecycle handlers are reached with **no authorization** beyond master-only.

**(d) Silent-skip paths.** `ApplyUserSliceLimits` writes the drop-in and never reads a single applied value back (`manager_spawn.go:890-928`; contrast the project's own no-silent-no-op rule in board `tasks.jsonl:280` §5). `provisionHostSSHKey` failing is a `logger.Warn` and spawn proceeds (`manager_spawn.go:317-323`, `host_key.go:26-33`) — an agent with no host key is still "spawned". `NewAuthInterceptor`/`NewJWTAuthInterceptor` collapse to `NoAuth{}` whenever `enabled == false` **or** the secret is empty (`interceptor.go:95-117`) — configuration typos become an unauthenticated daemon rather than a startup error (defended only by `CheckAuth` at `main.go:154`, which is one config-file edit away from the silent branch).

**(e) Fixes that weaken a requirement to fit a lane.** `TLSConnectionStateFromContext` exists to satisfy the mTLS requirement without a working seam; the test injects the value it needs (`internal/auth/mtls_test.go:383-394`, comment "We use the http.ServerContextKey trick that TLSConnectionStateFromContext looks for") — i.e. the test asserts the function's own assumption rather than any real deployment behaviour, and consequently tests cannot detect that `net/http` stores `*http.Server` at that key (`GOROOT net/http/server.go:244,3432`). `SECURITY.md:24` then keeps advertising the control. This is precisely the class the brief calls out.

**(f) Green-but-did-nothing.** Three live instances: (i) `destroy_home_policy: archive` is the config default (`config.go:430`) so a `userdel -rf` never runs unarchived, yet a large body of board work still describes plain `userdel -r` behaviour; (ii) the audit "one record per authenticated RPC" guarantee holds, but the *content* an IR needs is deliberately absent (`interceptor.go:206-209`) and lives only in snoopy→journald (`docs/exec-audit.md`) — a green audit trail that answers "who/when" but not "what did they run"; (iii) `docs/audit-2026-08.md` marks all 14 audit points PASS while the controls that matter for approval (transport, authz, anchoring) are absent from the checklist entirely — a PASS certificate over the wrong checklist is the purest example of green-but-did-nothing.
