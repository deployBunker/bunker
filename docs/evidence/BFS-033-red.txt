================================================================================
ATTRIBUTION — why the second PUT exists, measured rather than argued
================================================================================

Two questions decide the fix: how many times the kernel dispatches the resize for
ONE syscall, and what the re-issued dispatch publishes against.

1. THE KERNEL RE-ISSUES IT. One truncate(2), TWO size-carrying Setattr dispatches,
   traced with a temporary line in node.Setattr (BFS033_TRACE=1):
  BFS033-TRACE setattr path=src/target.txt size=48 fh_nil=true valid=0x208
  BFS033-TRACE setattr path=src/target.txt size=48 fh_nil=true valid=0x208
  dispatches: 2
   The same run's PUTs (compare the If-Match of the second with the first):
  # method   status  req_bytes  if_match                              path
  11 PUT      412     48         sha256:4435dba64cd01241ed5200836b30e81f5 /dav/src/target.txt
  13 PUT      204     48         sha256:2be53d0743bdd0be44d38e264a276eb1d /dav/src/target.txt

   The re-issued dispatch carries the base SPEC BFS-005 §5.2 rule 3 adopted from the
   refusal (X-Bunker-Current-Hash = the concurrent edit's hash) — which is exactly what
   the re-read-and-retry loop needs, and exactly why the refused write landed.

2. THE RE-ISSUE IS BOUNDED. With a probe build that refuses EVERY resize (so the
   refusal cannot be escaped by the re-issue), the kernel dispatches it TWICE and
   stops: the caller receives ESTALE, no PUT is made, nothing hangs. That is what makes
   an enforcement that refuses the re-issue safe:
  dispatches under always-refuse: 2
    |   truncate to 48          : REFUSED — OSError: [Errno 116] Stale file handle: '/tmp/bfs033/run-always-refuse/mnt/src/target.txt' (errno=116 ESTALE)
    |   target unchanged           : True
    |   PUTs on src/target.txt (proxy trace): 0
    |   PUT 412 count=0  PUT 2xx count=0

3. THE RETRY IS ESTALE-SPECIFIC (BFS-012's experiment, re-stated): with the conflict
   errno changed to EIO the refusal held with ONE PUT, because the kernel does not act
   on EIO. The verdict is kept (ESTALE names the recovery: re-read this one file) and
   the ENFORCEMENT is what this row adds — not a change of errno.
