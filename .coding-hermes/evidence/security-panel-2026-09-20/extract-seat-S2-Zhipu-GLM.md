1. SIGN-OFF VERDICT
======================================================================

DO-NOT-APPROVE — not because the isolation engineering is weak (the /tmp/PAM/scratch boundary and audit chain are genuinely well-built), but because the control plane around it fails the team-use bar on three fronts a security team will hit in the first hour of review: (1) the daemon's default posture is bearer-token over plaintext HTTP on all interfaces with TLS off by default (internal/config/config.go:374, config.example.yaml:17-18 "Leave disabled for plaintext"), and the shipped deployment pattern demonstrates exactly that on a public IP (docs/integration.md §2, 78.46.173.180:18080); (2) authentication failures are invisible by design — the audit interceptor is composed inside auth so failed-auth attempts produce zero audit records (internal/server/server.go:208-219), there is no rate limiting or lockout anywhere in the RPC path, and the default token-only auth path compares the bearer token non-constant-time (internal/auth/interceptor.go:70); (3) the supply chain for the rootless-docker installer is an unpinned curl to get.docker.com with no checksum verification (internal/agent/rootless.go:22,242). There is no threat model document, no RBAC beyond master/agent-scope, no secret rotation or revocation story, and no incident runbook. Approve only after the BLOCKER list in §3 is closed.

B — AGENT ISOLATION

C-6 | CONTRADICTED as product wording | SECURITY.md:30: "Out of scope: … compromise of the host system by a user with root in their own container (containers are designed for root access)." Two defects for a security-team audience. (1) It silently swaps "container escape" for "compromise by a user with root in their own container" — a reviewer cannot tell whether kernel-level escape from an unprivileged userns is in or out of the model, what the blast radius is stated to be (an unprivileged host user, cgroup-bounded — which is the actual, defensible claim the code makes), or whether host-kernel CVEs in unprivileged-userns attack surface are accepted risk. (2) It is the entire security model's only boundary statement — 1 line in a 30-line file, no threat model, no supported-configuration statement (no statement that egress is uncontrolled, that agents share the host network namespace, that the agent user is a real SSH account). Required rewording, minimum: "Threat: an agent attains root inside its own containers. Accepted: this equals an unprivileged host user (bunker-<id>) bounded by its cgroup and userns mapping; it must not reach other agents' homes, the daemon's credentials, or host root. Out of scope: host-kernel compromise from an unprivileged user (mitigated, not eliminated, by userns; operator must patch the host). NOT out of scope: any path from that unprivileged user to another agent's data or to bunkerd's secrets — report those." Plus a pointer to a real threat-model doc (owed, see §4).

D — AUDIT & FORENSICS

C-11 | SPLIT | Tamper-evidence is real against the agent side: hash-chained JSONL (each record digests its own canonical line incl. prev_hash — audit.go:331-351), chain reseeds across restarts (audit.go:164-178), rotation preserves the chain (audit.go:388-436), optional HMAC seals + remote shipping (audit.go:355-375, GAP-073), log is 0700-dir/0600-file root-owned (audit.go:126,130) — an in-container-root attacker (unprivileged host user) cannot read or write it. What such an attacker can still do: (a) nothing to history — confirmed; (b) FLOOD the future: each authenticated RPC writes a record, so a sub-key holder can generate unbounded volume (rotation keeps only 5MiB x 3 = ~20MiB, audit.go:20-26 — flood evicts evidence past the window); (c) pre-rotation segments are only protected if seal_key/ship_to are configured — both default OFF (config.go:459-462), and an unkeyed SHA-256 chain is trivially recomputable by anyone who obtains the file (host compromise), which the seals exist to catch but nobody turns on. Also the audit subsystem FAILS OPEN: if the log cannot be opened, the daemon warns and serves WITHOUT audit (server.go:60-80) — tamper-evidence that quietly disappears.

C-12 | SPLIT | Good: `bunker audit status/verify/list/export` exist with a documented record schema and first-bad-index reporting (docs/audit.md; verify.go:37; QueryAudit RPC service.go:912-921). Missing for incident response: (1) auth-FAILURE records — the interceptor sits inside auth, so "failed-auth attempts never produce audit records" (server.go:208-212, comment is explicit): the single most important forensic signal in a token-guessing incident does not exist; (2) no remote verify — verify/status are local-only (docs/audit.md §commands), so an responder must SSH to each host; (3) retention is 3x5MiB with no archival default (audit.go:20-26) — a busy multi-agent host churns that fast, and shipping is opt-in; (4) no correlation key tying audit records to the snoopy exec trail other than agent_id + timestamp (docs/exec-audit.md §2 is manual journalctl); (5) no integrity check on the snoopy/journald half at all (host-journal trust is assumed); (6) no alerting hook (ship_to is fire-and-forget, ship.go).

F — OPERATIONAL SECURITY

C-14 | ANSWER — the concrete scenario | Day 2 of team use: an engineer puts BUNKER_TOKEN=<master> into a CI variable / ~/.bashrc / a cron unit (the documented patterns — internal/cli/client.go:37-44 resolves token from entry, viper config, or env), and the team's bunkerd is reachable over plaintext HTTP because TLS ships off (C-3) and the quickstart never forces it. One compromise of that machine's env, one laptop on a hostile network with the demo IP in ~/.config/bunker/config.yaml (78.46.173.180:18080, plaintext per docs/integration.md §2), or one packet capture on the office LAN yields the MASTER token — which is a full admin capability: spawn agents, exec arbitrary shell as any bunker-* user, destroy everything (service.go:303-371,541+). The attacker's activity then generates audit records attributed to "master" (docs/audit.md caller field), auth failures are invisible (C-12), and there is no way to revoke or rotate the token short of editing the config and restarting every daemon (C-2/C-13). The missing control is a cluster of three: TLS-on-by-default (or refuse remote bind without it), scoped/rotatable credentials with a revocation command, and auth-failure audit + rate limiting. Secondary candidate with equal realism: the unpinned get.docker.com fetch (C-10) poisoning a spawn image pipeline.

6. REPEAT-OFFENSE SECTION
======================================================================

(a) credential/key paths leaking: the spawn keypair transits host /tmp with a predictable name — internal/agent/manager_spawn.go:259 (keyFile = os.TempDir()/bunker-key-<id>), removed only at 563-564/168-173. Same class as the historical ssh-agent/MaxAuthTries key-path finding (GAP-009 foreman note, board line 18): daemon credentials parked in a shared-adjacent location for convenience.
(b) success-marker strings as state: capability advertising via the literal string "isolation-grant" in --version, with the admission in-comment that "a version number cannot prove the grant" — internal/agent/isolation.go:164-177; the 419-line daemonversion.go skew-probe apparatus exists because strings-as-proof keeps failing; the e2e culture of VERIFY-PASS echo strings is the same bet.
(c) state ladders: spawn state is spread across tracker (memory) + agents.jsonl registry + spawn-failures.jsonl + systemd units + /etc/subuid — reconcile.go exists to re-derive truth, and GAP-070's whole fix history (board lines 65-70 region) is this ladder losing rungs on restart. Current residual: apikey sub-keys are a ladder rung that lives ONLY in memory (apikey/manager.go:16-27) while the registry pretends durability.
(d) silent-skip paths: the daemon serves WITHOUT audit when the log fails to open — internal/server/server.go:60-80 ("Failure is non-fatal … never blocks daemon startup"); invalid ship_to → warn + local-only (server.go:68-74); provisionIsolation best-effort failures warn and continue (isolation.go:208-226). Each is individually defensible; collectively they are the exact class that produced "bunker mount cannot mount any agent" at HEAD c50f7b3 while gates stayed green.
(e) fixes that weaken a requirement to fit a lane: GAP-073's shipping/sealing shipped OFF by default to avoid breaking existing deployments (audit.go:74-77 "Both default to off"); auth-disabled remains a supported mode with only a stderr warning (main.go:154-159) rather than refusing, because the demo fleet needed it; TokenAuth kept the naive compare (interceptor.go:70) while its sibling got the fix (jwt.go:153).
(f) green-but-did-nothing: docs/ci-proto-rate-limit.md:16-19 documents CI runs whose protobuf step FAILED but "still reported conclusion=success"; the JWT masterKey field is stored, set to the secret, and never used in any validation path (jwt.go:33,45 — dead security theater); MTLSAuth + NewMTLSInterceptor are fully implemented, fully tested, and wired to nothing (mtls.go:135-137, zero call sites) while SECURITY.md sells mTLS — the strongest green-but-did-nothing instance in the tree.
