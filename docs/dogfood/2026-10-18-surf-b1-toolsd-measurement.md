# SURF-B1 — toolsd service justification: per-call cost + daemon cost model (MEASURE FIRST)

**Date:** measured 2026-10-18 evening (all times UTC-05:00).
**Task:** SURF-B1 — *Measurement: toolsd service justification* (companion to `2026-10-17-surf-b1-toolsd-measurement.md`, which covers the invocation-ledger census and the ADR threshold derivation; this document adds the **daemon cost model** — memory, startup, per-call IPC — measured live, plus refreshed frequency data).
**Blast radius:** read-only analysis + scratch processes under `/tmp` + this document. Zero code changes. No live daemon was touched (measurements used a scratch socket owned by this session).
**Verdict up front: NO — an in-agent (per-agent) toolsd service is not justified on today's data.** Measured locally, the daemon's per-call cost over a keep-alive unix-socket HTTP round trip (**3.86 ms/call, n=100**) is *identical* to one direct CLI exec (**3.90 ms/call, n=100**) — the daemon buys no local speed at all. Its only latency win is on the remote exec path (~1.21 s/call saved, measured 10-17), and the call volume that would amortize it does not exist: the clean 29-day ledger holds **289 invocations fleet-wide (~10/day)**, of which the fsops verbs (`read`/`write`/`list`) — the ones a socket service exists to accelerate — account for **6 calls, all generated by the 10-17 measurement session itself**. The carry cost is real but small (~9–10 MB RSS per agent measured). Numbers below.

Caveats stated plainly: (a) the bash timing loops add per-iteration shell overhead to BOTH the exec arm and the fresh-connection socket arm (they cancel in the comparison); the keep-alive arm has zero loop overhead and lands at the same ~3.9 ms, so the per-call figure is robust. (b) The first startup attempt printed 4,125 ms — a measurement artifact (the readiness curl was mis-built, so the poll loop ran to exhaustion); corrected runs measure 15–29 ms. (c) All numbers are this-box-local; the 10-17 doc shows the same-host tunnel makes 1.21 s the FLOOR for remote transport — inter-host legs only increase it.

## 4. Recommendation

**NO — do not run toolsd per-agent today.** Evidence:

1. **The speed argument is void locally.** Per-call cost over the socket (3.86 ms) equals one direct exec (3.90 ms). A per-agent daemon does not make local calls faster; the process-start cost it eliminates is already at parity with HTTP client per-request handling. Any justification must therefore come from the REMOTE path or from semantics (push/session state), not from latency.
2. **The remote win has no workload.** Saving ~1.21 s/call matters only at volume, and the ADR break-even is ~590 calls/day (10× margin ~5,900/day). The fleet made ~10 calls/day over 29 days, zero of them through the remote exec path (no live agents), and the fsops verbs a socket service exists to serve have **never been called organically** (6 calls in 29 days, all self-generated by measurement).
3. **The carry cost is small but buys nothing.** ~9–10 MB RSS per agent plus a unit-file lifecycle (the SURF-001 recipe already exists for the no-new-code alternative). Cheap — but strictly a cost at today's volume.

**CONDITIONAL yes, if any of these re-measure conditions fire** (same triggers as the 10-17 doc, now with the cost model attached):

- GAP-096 (toolsd in agent images) lands and real agent editing sessions appear → re-run the census; if sustained exec-delivered volume approaches ~590 calls/day, the daemon saves ~1.21 s × N with a measured 9–10 MB/agent price tag — clearly worth it at that point.
- A product need for subscription/push (Trigger 1) or long-lived session state emerges — these are impossible on the exec path regardless of volume, and the 56 KB descriptor surface (22 tools) is already socket-ready.
- Inter-host agent placement appears — the 1.21 s/call floor only grows, strengthening the remote-path case at unchanged break-even.

## 5. Honest limits

- Single box, single binary build (`toolsd version dev`), n=100 per arm, warm page cache; p99 tails not characterized. The exec-vs-socket parity result is robust (two independent arms agree within 1%), the absolute ~3.9 ms is load-dependent (10-17 measured ~7 ms process floor under fleet load).
- The keep-alive arm used curl as the client; a native Go HTTP client may shave the 3.86 ms further, which would only strengthen the "no local gain" conclusion.
- Frequency data covers ONE caller box (the only one with a ledger — agent-side ledgers die with agent homes). If other boxes run toolsd, their traffic is invisible here; no evidence any does (`bunker list` empty on all servers).
- The ~590/day break-even inherits the 10-17 doc's 3-engineer-day carry estimate (assumption, labeled there); the verdict has 100× headroom against it.
