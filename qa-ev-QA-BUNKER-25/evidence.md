# QA-BUNKER-25 — clean-machine `proto/bunker/v1/bunkerv1connect` build failure

Row: `QA-BUNKER-25` — "[P1] Clean-machine bunkerv1connect build failure on JIT agent —
not reproducible locally (env-class, 2 cells)".
Worktree: `/home/kara/worktrees/bunker-QA-BUNKER-25`, branch `wt/QA-BUNKER-25`,
base `f04d8a12`. Fix commits: `ff3e1dc2` (vendor/), `bf29eb05` (proto stamp).

## Verdict

Two REPO-SIDE defects that break a fresh checkout were found, reproduced
deterministically, and fixed. Neither is a protoc-gen-connect-go version problem,
and neither needs cgo or a build tag.

1. **A top-level `vendor/` directory holding no Go code** (`vendor/sshfs`, added by
   MOUNT-015 in `f3d55824`) made the `go` command select `-mod=vendor` for the whole
   module. Every `go build` / `go test` in a **fresh checkout** then died with
   `inconsistent vendoring`, which is the clean-machine signature this row recorded.
   A developer box that had run `go mod vendor` (or simply had a warm tree) never
   showed it — that is why "not reproducible locally" held.
2. **The protobuf freshness stamp keyed on every tracked YAML in the repo**, and had
   itself drifted (`608f175b`). So `bash .github/scripts/ensure-proto.sh` reported
   "regeneration needed" on **every** CI run and on **every** fresh-system pass,
   calling `buf generate` against the BSR — a network dependency for a step that
   produces no diff at all. On a network-restricted JIT agent that is a live
   failure path for the proto packages.

The historical 2026-09-26 per-package `[build failed]` line at `4145cbe` (before
`vendor/sshfs` existed) is **not** reproduced and its cause is **not** in the current
tree — see "Residual" for what is and is not proven.

## Hypotheses tested and rejected

* **Toolchain mismatch** — `toolchain go1.26.10` with a host on an older Go either
  GOTOOLCHAIN-downloads the toolchain or fails **every** package; it cannot produce a
  single-package failure. The QA cells themselves reported `go 1.26.5` present.
* **Stale protoc-gen-connect-go** — `bunker.connect.go` asserts
  `connect.IsAtLeastVersion1_13_0`; connect v1.21.0 defines exactly
  `0_0_1 / 0_1_0 / 1_7_0 / 1_13_0` (`connect.go:41-44`), so the assertion holds for
  the committed `go.mod`. The package's own `SKILL.md` claimed the assertion was
  `IsAtLeastVersion1_17_0` — **false**, and exactly the kind of stale claim that sends
  an investigation down a version hunt. Corrected in `ff3e1dc2`.
* **Missing generated code on the clean host** — the generated files are committed;
  no `go:generate`, and `buf generate` reproduces them byte-for-byte (below).

## Defect 1 — stray `vendor/` forced `-mod=vendor` (commit `ff3e1dc2`)

### Reproduction (pristine checkout of the base)

```
$ git worktree add --detach /tmp/qa25-clean f04d8a12
$ cd /tmp/qa25-clean && ls vendor
sshfs
$ go build ./proto/bunker/v1/bunkerv1connect/
go: inconsistent vendoring in /tmp/qa25-clean:
        connectrpc.com/connect@v1.21.0: is explicitly required in go.mod, but not marked as explicit in vendor/modules.txt
        ... (one line per module)
rc=1
$ go test ./... -count=1 -short
go: inconsistent vendoring in /tmp/qa25-clean: ...          rc=1
```

`ls -la vendor/` shows a single entry, `sshfs/`, and **no `modules.txt`**.

### Mechanism (from the Go toolchain source, not from memory)

`cmd/go/internal/modload` `readVendorList`, Go 1.26:

```go
f, err := fsys.Open(filepath.Join(vendorDir, "modules.txt"))
if errors.Is(err, os.ErrNotExist) {
    // Some vendor directories exist that don't contain modules.txt.
    // This mostly happens when converting to modules.
    // We want to preserve the behavior that mod=vendor is set (even though
    // readVendorList does nothing in that case).
    return false, nil
}
```

The **absence** of `modules.txt` does not opt out of vendoring — it keeps `mod=vendor`
and leaves the vendored module list empty, so every `require` in `go.mod` reads as
"not marked as explicit". Confirmed by two control arms in the same worktree:

```
$ mv vendor vendor.hold && go build ./proto/bunker/v1/bunkerv1connect/   # rc=0
$ mv vendor.hold vendor                                                    # restore
$ GOFLAGS=-mod=mod go build ./proto/bunker/v1/bunkerv1connect/           # rc=0
```

The directory came from MOUNT-015 (`f3d55824`), which copied the patched upstream
sshfs tree to `vendor/sshfs/` for a visible diff — a **non-Go** project in the one
directory name the go command reserves.

### Fix

* `git mv vendor/sshfs probes/sshfs-readdirplus/upstream/` (36 files, 100% rename) —
  it now sits next to the patch and probe harness that own it;
  `probes/sshfs-readdirplus/build.sh` clones the pinned upstream commit itself, so no
  script consumed the old path. The only other reference was the probe README.
* `.gitignore`: carve-out moved to `!probes/sshfs-readdirplus/upstream/test/*.py` and
  the reason recorded inline.
* `scripts/check-go-vendor-dir.sh` — FAILs when `vendor/` exists without
  `modules.txt`, or holds foreign-language sources (a vendored *project*, not a
  module vendor tree), and names the remedy. Wired into
  `scripts/pre-release-check.sh` (check 0, tree **and** `--tag` modes) and into the
  tier-0 CI job ahead of `go build`.
* `proto/bunker/v1/bunkerv1connect/bunker.connect_smoke_test.go` — the package had no
  tests, so a battery could only ever print `? ... [no test files]` for it. It now has
  a real `httptest` round trip through the generated client **and** handler (the stub
  implements `ServerInfo` and embeds the handler interface for the other 21 RPCs) plus
  a procedure-constant table, so a healthy tree prints the positive
  `ok github.com/deployBunker/bunker/proto/bunker/v1/bunkerv1connect` line the
  acceptance criteria ask for.

### Verification

Pre-fix (pristine base checkout): `go build ./...` rc=1, `go test ./...` rc=1,
`0` packages `ok`.
Post-fix (pristine checkout of the fix): see the log below — AC1 rc=0 with the literal
`ok ...bunkerv1connect` line, `go build ./...` rc=0, full short suite green.

## Defect 2 — proto freshness stamp keyed on every tracked YAML (commit `bf29eb05`)

### Measured

```
# base f04d8a12
$ RAW="$(git ls-files -- '*.proto' '*.yaml')"; printf '%s\n' "$RAW" | sha256sum
→ proto-gen-v1-e7b35c30… (11 paths)
$ cat proto/.codegen-fresh
→ proto-gen-v1-d8d1e3a8…   ← last written in 608f175b, before
                              internal/fleet/inventory.yaml landed and
                              proto/bunker/v1/bunker.proto changed
$ PATH=<buf stub>:$PATH bash .github/scripts/ensure-proto.sh
proto: inputs changed (stamp d8d1e3a8 != e7b35c30) — regeneration needed
proto: buf generate attempt 1/5
proto: NEEDED-and-DONE
```

The 11 inputs included `.gitreins/config.yaml`, `.gitreins/tasks.yaml`,
`.vfs/manifest.yaml`, `config.example.yaml`, `examples/*.yaml`,
`internal/fleet/inventory.yaml` and a vendored project's
`.pre-commit-config.yaml`. Adding or removing **any** YAML file anywhere re-arms
`buf generate`.

And regeneration is a no-op, which is what made the drift pure cost:

```
$ buf generate            # buf 1.72.0, remote plugins pinned in buf.gen.yaml
$ git status --short
(no output — committed generated code is byte-identical to a fresh generation)
```

### Fix

* Input set narrowed to `'*.proto' 'buf.yaml' 'buf.gen.yaml' '**/buf.yaml'
  '**/buf.gen.yaml'` (11 paths → 2: `proto/bunker/v1/bunker.proto`, `buf.gen.yaml`).
* Stamp refreshed **through the script's own code path**, so the value is the one the
  script computes: `proto-gen-v1-9988cc55…`; the next run prints `proto: SKIPPED`
  with no BSR call.
* Step 2b **stamp enforcement**: when a generation *had* to run, the script now fails
  the job if `proto/` (generated code or stamp) differs from the commit, printing
  `::error::proto generation drifted from the committed tree` plus the one command
  that fixes it (`PROTO_STAMP_ENFORCE=0` opts out). A stale stamp used to be
  invisible; it is now a loud, one-time failure.

### Three-arm verification (pristine worktree, fixed script)

```
A fresh stamp       → proto: SKIPPED                                          rc=0
B corrupted stamp   → generate runs → ::error::proto generation drifted …
                      + " M proto/.codegen-fresh"                             rc=1
C restored stamp    → proto: SKIPPED                                          rc=0
```

## Residual (not proven here)

* The 2026-09-26 single-package `[build failed]` at `4145cbe` is **not reproduced**.
  At that commit there was no `vendor/` directory, no cgo, no build tag, and the
  connect-version assertion could not fail against the committed `go.mod`. The row's
  env-class classification stands for that specific observation.
* If it recurs on a JIT agent, capture this set before anything else — it separates
  the remaining classes in one shot:
  `go version`, `go env GOFLAGS GOTOOLCHAIN GOMODCACHE GOPATH CGO_ENABLED`,
  `ls -d vendor && ls vendor`, `go list -m connectrpc.com/connect`,
  `bash .github/scripts/ensure-proto.sh` (SKIPPED vs NEEDED-and-DONE), and the full
  `go test ./... 2>&1` output (stderr included). Note the shape difference: a
  vendoring fault prints ONE fatal `go: inconsistent vendoring` block and no package
  lines, while a per-package `FAIL … [build failed]` means that package's own
  compilation failed — a different class.
* `internal/fsmount` `TestBFS039CancelledPublicationDoesNotCloseTheBuffer` is flaky
  under full-suite load (observed once). Out of scope for this row; worth its own row.
