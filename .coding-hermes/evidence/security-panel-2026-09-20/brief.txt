on a shared box. One Linux user = one Docker daemon = one isolated agent. Claims: "complete
isolation without Docker-in-Docker, Sysbox, or full VMs". Density claim: 20+ agents on one
bare-metal host.

**A — Control plane (the daemon is the crown jewel)**
- C-1  The `SECURITY.md` "security model" list matches what the code actually implements
       (each of its 5 bullets is real and correctly described).
- C-2  Auth is sound: token/JWT generation, scope enforcement, and the mtls path are

- C-3  Transport default posture is safe: what is the DEFAULT when TLS is off — does the
       daemon refuse to run, warn, or silently serve plaintext on a reachable interface?
- C-4  Authorization between agents: nothing lets agent A's credentials act on agent B.
- C-5  Destroy/renew/register RPCs are authorized at least as strictly as spawn.

**B — Agent isolation (the product's core promise)**
- C-6  Container escape: `SECURITY.md` says root-in-own-container is OUT OF SCOPE. For a
       SECURITY-TEAM audience, is that defensible as written, or must it be re-worded
       (and how)? Judge the WORDING as product risk, not the kernel reality.
- C-7  The per-agent isolation claims (own dockerd, userns remap, SSH key isolation)
       hold in the code and are not merely aspirational.
- C-8  What host-accessible surfaces does an agent user still have beyond its own
       container — anything that lets agent A read or affect another agent's data?

**C — Provisioning & supply chain**
- C-9  `useradd`/`userdel`/`subuid`/`chown`/`systemd-run` call paths: any injection or
       TOCTOU class where an agent-influenced value ([agent-id], paths) reaches a shell

- C-10 Binary/install supply chain: how the binaries and the rootless-docker installer
       get onto a host, and whether that path is pinned/verified.

**D — Audit & forensics**

**E — Secrets**
- C-13 Secret handling end to end: the bunkerd token, JWT secret, per-agent SSH keys, and
