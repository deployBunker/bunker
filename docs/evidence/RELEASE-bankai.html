The win survives WAN latency (the "both DCs" risk, partially de-risked)

At dedi-2's own measured 185.2 ms RTT (delay relay, both arms in one run, delay verified in the path first):

snapshot walk     118 ms
no-snapshot walk  1416 ms      = 12.0×

118 ms is below one round trip — and that is the real finding: the tree is fetched once at mount, and every later whole-tree walk is served locally. That is why the ratio grows with latency: the no-snapshot arm pays the RTT per request, the snapshot arm pays it once.

The lever is concurrency; the protocol is only the carrier

h2  conc 1 → 8:   12.231 s → 2.008 s   (7.7449×)
h1  conc 1 → 8, ONE connection:  0.9995×  (does NOT degrade — correct)
carrier test at the same conc=8, changing ONLY the connection count:
    h1  11.966 s (1 conn) → 1.847 s (8 conns)  = 6.4777×  — level with h2

BFS-016 refined this: concurrency is the lever for independent requests, the snapshot is the lever for a whole-tree walk. Two mechanisms; the client has both.

3 · Findings — the most valuable output of this release

Every item below was found by measurement, most by rows whose job was to test rather than build. All are filed rows with their own acceptance criteria, not footnotes.
The client is not yet safe for editing a working tree. Reproduced independently by the driver, twice.

BFS-025 (P0) — truncated reads. A path merely stated, then replaced with longer content on the agent, returns a fragment with rc=0: 5 bytes of a 66-byte file. Not stale bytes — new bytes, truncated, presented as success. A build or checksum gets a wrong answer with no error.

BFS-024 (P0) — stale reads. A path already read keeps serving pre-edit bytes after an agent-side replacement.

BFS-026 (P0) — the root cause. The client's invalidation depends on server ops that do not exist: of 8 declared E-4 ops the server implements 2, and events/watch answer capability_unavailable, "slice C5". The client detects and reports this honestly ("mechanism": "none") — but with no third mechanism, nothing ever invalidates.

BFS-030 (P0) — data loss on a failed rewrite. > on an existing file truncates it, the O_TRUNC half lands, then the write fails — leaving an empty file where the content was. In-place r+b/append are unreachable entirely.

BFS-033 (P0) — the conflict refusal does not hold live. A unit test passes; through the mount a 412 is recorded in conflicts.jsonl and then a 204 lands, caller sees success. Attributed below the client's API and specific to the ESTALE verdict (with EIO the refusal holds). The detection is sound and hash-based; the enforcement fails. A logged-then-bypassed refusal is worse than none — it manufactures an audit trail claiming a protection the user did not get.

The bound does not bound

BFS-031: at a 1 KiB bound the cache directory reached 30,689 B = 29.97× while the client's reported figures stayed inside — status.json/conflicts.jsonl sit outside used_bytes. BFS-032: oversize_bypasses can never move (pre-filtered before the counter). A counter that cannot move is a gap, not a green check.

Platform seam

The !linux seam did not compile for any non-Linux platform — found by the row's own acceptance sentence, fixed, with a committed cross-GOOS guard. BFS-028 cli/umount.go is POSIX-only, the one site stopping GOOS=windows go build ./.... BFS-029 fsclient/errors.go reaches for syscall.EREMOTEIO, undefined on darwin/freebsd, despite the package's own portable errno mechanism. Windows decision: WinFsp via cgofuse, opt-in; the OS redirector rejected because it cannot express the concurrency knob or carry the snapshot op — the two measured things that make the client fast.

Correctness + hygiene

BFS-018 symlinks do not round-trip (a symlink appears as a regular file containing its target — a repo with symlinks is corrupted on first write-back). BFS-019 readdir can return empty while entries exist. BFS-020 a created file cannot be renamed until published, breaking git's lock-then-rename and leaving <ref>.lock on the tree. BFS-021 >> loses bytes. BFS-022/023 the battery instrument carries a +110 ms timeout constant and the op deadline compounds to 60 s against a documented 30 s. BFS-017 the guard fails on host load, not code.

4 · Honest ledger — what this release did NOT establish

  • The both-DCs rule is NOT satisfied. Every client measurement is loopback or a simulated RTT. The real DC leg is blocked on a Tailscale auth click.
  • No Windows anything. No Windows code written and no Windows result claimed, because none could be run — a stub that cannot compile would make the repo look ported while nothing on Windows had ever run. Mint: no work, with reasoning.
  • Delegation (PRD slice C5) — the ~80× whole-tree win — is declared and honest but NOT BUILT. Four of eight E-4 ops answer capability_unavailable. Largest remaining gap; root cause of BFS-026.
  • Nothing about stalls at WAN distance. The WAN measurement is walk time only.
  • Named SKIPs, recorded rather than passed: the live touch-only arm (it served stale bytes), conflict refusal through a plain overwrite, concurrent-write bound arms, the 1 h TTL, whether the FUSE kernel or the VFS issues the retry, and the > data-loss shape reported without being root-caused to a line.

6 · Where the next work is

The release's deliverable is complete; its findings are now the work. Five are P0: BFS-025 (truncated reads — silent corruption), BFS-030 (> empties a file — data loss on a failed rewrite), BFS-033 (refusal logged then bypassed), BFS-024 (stale reads), BFS-026 (the slice C5 gap they share a root with).

The one-line verdict: bunker-fs is fit for reading immutable data, and not yet safe for editing a working tree — which is exactly the line the next wave should cross, starting with BFS-026 because it is the root cause of three of the five.
